# CodeMate 设计说明

## 1. 定位

终端里的本地 coding agent，Go 实现。在用户当前工作区工作：读文件、改文件、执行命令，按多轮任务推进，高风险操作执行前需确认。

设计目标不是功能数量，而是让一次多轮任务**可约束、可恢复、可复盘**。三条对应三个层次：

- 可约束：工具副作用受审批与边界控制
- 可恢复：会话与任务状态落盘，中断后能接上
- 可复盘：每次运行产出结构化事件流，事后可查

## 2. 范围

做：

- 单进程、单工作区、命令行交互
- 多轮工具调用闭环
- 权限审批与文件改动评审
- 会话持久化与续跑
- 运行事件落盘
- 上下文预算控制与压缩
- 固定任务集的离线评测

不做：

- 多用户、多租户、鉴权
- Web UI、IDE 插件
- 多 agent 编排与任务委派
- 向量检索与代码库索引
- 模型训练与微调

不做不等于以后不做，是不在本版本的验收范围内。每一条都有明确理由：前三条会把项目推向服务端与前端，后两条的成本高于收益。

## 3. 运行模型

一次任务的生命周期：

1. 启动时解析参数、加载配置、发现技能、构建工具注册表、初始化权限管理器、装配系统提示词
2. 创建运行目录，写 `run.start`
3. 进入回合循环：请求模型 → 解析返回 → 执行工具 → 结果回灌 → 判定是否结束
4. 每轮结束写 `turn.end`，每次模型调用写 `model.call`，每次工具调用写 `tool.call` 与 `tool.result`
5. 退出时写 `run.end`

回合的终止条件有四种：模型给出最终回答、模型提出澄清问题、达到步数上限、发生不可恢复错误。四者在事件里可区分。

## 4. 分层与包边界

`cmd/codemate` 只做装配，不含业务逻辑。

`internal/agent` 是回合循环，只依赖 `message` 与 `tools` 的接口，不知道终端、不知道会话存储。

`internal/message` 定义消息与步骤的类型，是整个系统的类型地基。

`internal/tools` 定义工具注册表、JSON Schema 校验与内置工具。工具不知道审批是谁做的，只接收一个权限接口。

`internal/permissions` 与 `internal/workspace`、`internal/filereview` 组成安全边界：路径越界、危险命令、文件改动三类检查，以及写盘前的 diff 生成。

`internal/model` 把不同厂商的接口归一成统一的 `Step`，OpenAI 兼容与 Anthropic 兼容两套适配器。

`internal/runs` 负责运行工件，只依赖标准库，不认识 agent 的类型，通过一个只含 `Event(string, map[string]any)` 的接口接收事件。

`internal/session` 是终端侧的外壳，负责输入循环、斜杠命令、会话存档与调用 agent。

`internal/mcp` 把外部 server 的工具挂进同一个注册表。

`internal/skills` 负责技能发现与加载。

依赖方向单一：`cmd` → `session` → `agent` → `tools` / `message`；`runs` 与 `permissions` 是叶子，不被上层反向依赖。

## 5. 事件模型

每次运行一个目录：`<workspace>/.codemate/runs/<run_id>/events.jsonl`。

`run_id` 由 UTC 时间戳加六位随机十六进制构成，保证同一秒内多次启动不冲突。

每条事件一行 JSON，字段固定：

- `seq` 自增整数，从 1 开始，同一运行内单调递增
- `ts` UTC 时间，RFC3339 纳秒精度
- `type` 事件类型
- `data` 类型相关的载荷

已定义的六种类型：

`run.start` 载荷含工作区路径。`model.call` 载荷含步号、耗时、停止原因、是否成功。`tool.call` 载荷含工具名。`tool.result` 载荷含工具名、成功标志、耗时、输出字节数。`turn.end` 载荷含总耗时、模型调用次数、工具调用次数、是否成功。`run.end` 载荷含退出原因。

写入策略：追加写、单文件、行级原子。写入失败不打断任务，记录首个错误并在关闭时返回。并发调用由互斥锁保护序号与写入。

## 6. 工具与审批

工具统一走注册表：入参先做 JSON Schema 子集校验，再进入执行。工具内部 panic 会被捕获并转成错误结果返回模型，不让进程崩。

三类操作需要审批：路径访问越出工作区、命令执行、文件修改。拒绝不停任务，拒绝原因作为工具结果回传，模型可另选路径。

文件修改在落盘前生成 unified diff 供确认，确认失败不覆盖原文件。

## 7. 上下文预算与压缩（待实现）

目标：长会话不撞上下文窗口，且压缩本身不破坏可继续性。

机制：请求前估算当前上下文规模，超过阈值时把较早的消息压成摘要，保留最近若干轮原文。摘要与原始消息分开存，恢复时按检查点重建。

边界：压缩失败保留原历史并报错，不做半截替换；连续压缩有次数上限，避免反复压缩不收敛。

验收：同一段三十轮对话，记录压缩前后单轮请求的 token 数；压缩失败场景有一条可复现的测试。

## 8. 任务状态与恢复（待实现）

目标：进程退出或上下文超限后，任务能从断点继续，而不是重放整段历史。

机制：定义任务状态（运行中、等待审批、已压缩、失败、完成），状态与检查点落盘；恢复时校验工作区指纹，不一致则拒绝恢复。

边界：工作区被外部修改后不静默续跑，宁可要求重来。

验收：三种中断场景（超预算、手动中断、工作区被改）各有测试；工作区漂移的识别率为 100%。

## 9. 评测（待实现）

目标：改提示词或换模型之后，能判断能力是变好还是变差，而不是凭感觉。

机制：固定任务集加固定判定方式；指标包括任务完成率、平均模型轮数、平均 token、工具调用失败率。评测分两层：回归层跑全量任务集给出通过率，诊断层对失败任务归类到具体环节。

边界：任务集规模有限，结论只对这批任务成立，不外推。

验收：一条命令跑完全部任务并输出报告；同一任务集重复跑两次，通过率差异在可解释范围内。

## 10. 非目标与已知局限

单机单用户，没有并发与多租户设计。

命令执行靠审批与白名单，不是沙箱隔离；进程资源没有硬限制。

模型输出没有独立的验证阶段，正确性依赖模型自身与用户判断。

以上三条是当前版本的边界，写在这里是为了不让它们变成隐含假设。
