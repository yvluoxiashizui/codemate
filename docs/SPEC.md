# CodeMate 设计说明

## 1. 定位

终端里的本地 coding agent，Go 实现。在用户当前工作区工作：读文件、改文件、执行命令，按多轮任务推进，高风险操作执行前需确认。

设计目标不是功能数量，而是让一次多轮任务**可约束、可恢复、可复盘**。三条对应三个层次：

- 可约束：工具副作用受审批与边界控制
- 可恢复：会话与任务状态落盘，中断后能接上
- 可复盘：每次运行产出结构化事件流，事后可查

## 2. 范围

做：

- 单进程、单工作区、命令行交互
- 多轮工具调用闭环，工具调用用文本协议表达
- 权限审批与文件改动评审
- 会话持久化与续跑
- 运行事件落盘
- 分节上下文预算与裁剪
- 固定任务集的离线评测

不做：

- 多用户、多租户、鉴权
- Web UI、IDE 插件
- 多 agent 编排与任务委派
- 原生 function calling 与 MCP
- 向量检索与代码库索引
- 模型训练与微调

不做不等于以后不做，是不在本版本的验收范围内。前三条会把项目推向服务端与前端；原生工具协议与 MCP 会让工具层同时存在两套调用路径，与文本协议冲突，因此一并排除；向量检索与代码库索引的成本高于收益。

## 3. 运行模型

一次任务的生命周期：

1. 启动时解析参数、加载配置、发现技能、构建工具注册表、初始化权限管理器
2. 创建运行目录，写 `run.start`
3. 进入回合循环
4. 每轮：按分节预算拼装 prompt → 请求模型 → 解析应答 → 若是工具调用则执行并把结果写入历史 → 重复，直到解析出最终答案
5. 退出时写 `run.end`

回合的终止条件有四种：模型给出 `<final>`、解析失败达到次数上限、达到步数上限、发生不可恢复错误。四者在事件里可区分。

## 4. 分层与包边界

`cmd/codemate` 只做装配，不含业务逻辑。

`internal/agent` 是回合循环：拼 prompt、请求模型、解析、执行工具。

`internal/protocol` 定义提示词前缀构建与应答解析，是唯一知道 `<tool>` 与 `<final>` 格式的地方。

`internal/context` 负责分节渲染、预算分配与超预算裁剪。

`internal/tools` 定义工具注册表、参数校验与内置工具。

`internal/permissions` 与 `internal/workspace`、`internal/filereview` 组成安全边界。

`internal/model` 把不同厂商的接口归一成「输入一段 prompt，输出一段文本」。

`internal/runs` 负责运行工件，只依赖标准库，通过只含 `Event(string, map[string]any)` 的接口接收事件。

`internal/session` 是终端侧的外壳：输入循环、斜杠命令、会话存档。

`internal/skills` 负责技能发现与加载。

依赖方向单一：`cmd` → `session` → `agent` → `protocol` / `context` / `tools`；`runs` 与 `permissions` 是叶子。

## 5. 事件模型

每次运行一个目录：`<workspace>/.codemate/runs/<run_id>/events.jsonl`。

每条事件一行 JSON，字段固定：`seq` 自增、`ts` UTC 纳秒时间、`type` 事件类型、`data` 类型相关载荷。

已定义的类型：

`run.start` 含工作区路径。`model.request` 含轮次、prompt 字符数、各 section 的实际渲染长度。`model.response` 含耗时、应答字符数、解析结果类型、解析是否失败。`tool.call` 含工具名与参数。`tool.result` 含工具名、成功标志、耗时、输出字符数。`turn.end` 含轮次总数、工具调用次数、总耗时、是否成功。`run.end` 含退出原因。

写入策略：追加写、行级原子、互斥锁保护序号。写入失败不打断任务，记下首个错误并在关闭时返回。

## 6. 工具协议

工具在提示词前缀里以文本形式描述，包含名称、参数、是否需要审批、用途。

模型每次应答必须且只能是一个块：

```
<tool>{"name":"read_file","args":{"path":"a.go"}}</tool>
<final>回答正文</final>
```

多行内容用 XML 形式：

```
<tool name="write_file" path="a.go"><content>...</content></tool>
```

解析失败不重试同一次请求，而是把解析错误写进历史并重新拼装 prompt，让模型看到自己的格式错误。连续失败达到上限则终止本轮，并把最后一次原始应答写进事件。

## 7. 上下文预算与裁剪

一轮 prompt 分成五节：系统前缀、记忆、相关笔记、历史、当前请求。每节有预算与下限，当前请求不参与裁剪。

拼装后如果总长超过上限，按固定顺序收缩：先相关笔记，再历史，最后记忆与前缀；每次只收缩一个 section，收缩到下限为止，反复直到落进预算或没有可收缩的节。

裁剪方式是尾部截断，保留开头并追加省略标记。预算是字符数而不是 token。

裁剪记录写进 `model.request` 事件，事后能看出这一轮为什么变短。

验收：构造一段超预算的历史，记录裁剪前后各节长度与最终字符数；同一输入两次拼装结果必须完全一致。

## 8. 会话状态与恢复（待实现）

目标：进程退出后任务能接上，且不重读整段历史。

机制：存档保存原始历史与工作上下文两份；恢复时用工作上下文，原始历史保留用于审计。任务状态与检查点落盘。

边界：工作区被外部修改后不静默续跑。

验收：存档往返一致；工作区指纹不一致时拒绝恢复。

## 9. 评测（待实现）

目标：改提示词或换模型之后，能判断能力变好还是变差。

机制：固定任务集加固定判定方式；指标为任务完成率、平均轮次、平均 prompt 字符数、工具调用失败率。

边界：任务集规模有限，结论只对这批任务成立。

验收：一条命令跑完全部任务并输出报告；同一任务集重复跑两次，通过率差异可解释。

## 10. 非目标与已知局限

单机单用户，没有并发与多租户设计。

命令执行靠审批与白名单，不是沙箱隔离。

放弃原生 function calling 换来的是一致性与可控的 prompt 形态，代价是依赖模型遵循文本格式；格式遵从度差的模型会频繁解析失败。
